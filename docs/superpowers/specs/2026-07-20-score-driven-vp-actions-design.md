# Score-driven actions: eject / lower_vp / raise_vp

## Context

katana today has a single action (eject) driven by two raw metrics
(`missed_blocks`, `critical_alerts`) fetched separately from gnomonitoring
(`/missing_block`, `/admin/alerts`), combined via `require_all` AND/OR in
`internal/rules`.

gnomonitoring now exposes a computed per-validator health score at
`GET /api/reports/validators?chain=<chainID>`, aggregating sign rate, proposer
reliability, incident frequency and downtime into a single `score` (0-100) per
rolling/calendar window (`last_24h`, `current_week`, `current_month`,
`current_year`), with weights and caps tunable on the gnomonitoring side
(`report_score_*` in `admin_config`, no redeploy needed), and mapped to tiers
`Excellent ≥85 / Good ≥60 / Watch ≥30 / Critical <30`. See
`gnomonitoring/README.md` §"How the score is calculated".

The goal of this spec: replace the binary eject-only model with three
score-driven actions — **eject**, **lower_vp**, **raise_vp** — each
independently configurable, so katana can reward reliable validators with
more voting power and progressively demote unreliable ones before a full
ejection, instead of ejection being the only lever.

## Goal

- `internal/rules` decides **at most one action per validator per cycle**
  (`eject` / `lower_vp` / `raise_vp` / none) from the gnomonitoring score,
  using per-action numeric thresholds, per-action score windows, and a
  **configurable priority order** between actions (not hardcoded).
- `internal/proposal` generalizes to build a `ValoperChange` proposal with an
  arbitrary target voting power (not just `Power=0`), for all three actions,
  using a **fixed-step, non-compounding** delta model (see "VP delta model"
  below).
- `internal/lifecycle` keeps a single per-`(chain, address)` history but knows
  the action type of the last proposal, so an accepted `lower_vp`/`raise_vp`
  is not treated as terminal the way an accepted `eject` is.
- `internal/notify` generalizes its three messages (sent/accepted/rejected) to
  describe the action taken, not just ejection.
- Raw sub-metrics (`sign_rate`, `proposer_reliability`, `incident_rate_per_week`,
  `downtime_blocks`, `tier`) are **not** used as eligibility conditions — they
  are surfaced as human-readable context in the proposal description and
  notification text only. The score stays the single decision signal, so
  katana never re-derives weighting logic gnomonitoring already owns.
- The existing `exceptions` list is extended to protect against all three
  actions (today it only blocks eject), covering the gno core team whitelist
  use case.

This is a **breaking config change**: `conditions.missed_blocks` /
`conditions.critical_alerts` / `conditions.require_all` are removed.

## Config (`internal/config`)

```yaml
gnomonitoring:
  base_url: "..."
  api_token: ""                     # kept: some gnomonitoring deployments may still gate other endpoints
  timeout_seconds: 10
  reports_path: "/api/reports/validators"   # replaces missed_blocks_path + alerts_path

proposal:
  # First action in this list whose threshold matches, wins. Reordering is a
  # config change, not a code change. Default mirrors "most severe verdict
  # wins" (see "Cross-window conflicts" below).
  action_priority: [eject, lower_vp, raise_vp]

  min_voting_power: 100             # absolute floor; protects a small validator
                                     # from being driven to ~0 VP by repeated
                                     # lower_vp instead of a real eject
  max_voting_power_share: 15        # ceiling as % of the chain's total valset VP;
                                     # portable across networks with very
                                     # different total stake (unlike an absolute
                                     # number), and directly expresses the
                                     # governance concern (concentration), not
                                     # an arbitrary unit count

  cooldown: 720h
  rejected_backoff: 720h
  max_rejections: 2
  submit: run

  actions:
    # Thresholds below default to gnomonitoring's own tier boundaries
    # (Excellent >=85 / Good >=60 / Watch >=30 / Critical <30), so they mirror
    # a scale operators already read on gnomonitoring dashboards rather than
    # being invented numbers. The 60-84 (Good) band is an intentional
    # "stability zone" with no automated action, to avoid flapping a
    # validator between raise/lower over minor movements mid-scale.
    eject:
      score_below: 30
      window: current_month
      title_template: "Eject validator {moniker} ({address}) from the valset"
      description_template: |
        Automated ejection proposal generated by katana.
        Validator: {moniker} ({address})
        Score: {score}/100 (tier {tier}) over {window}
        Reason: {reason}
      # run_script_template: defaults to the existing Power=0 ejection script
    lower_vp:
      score_below: 60
      window: current_week
      # Step magnitude = min of the two caps below (see "VP delta model");
      # whichever is tighter for this validator's size wins.
      vp_step_percent_of_self: -20  # cap #1: never more than 20% of the
                                     # validator's own current VP in one step
      vp_step_percent_of_total: -2  # cap #2: never more than 2% of the
                                     # chain's total valset VP in one step
      title_template: "Lower voting power of validator {moniker} ({address})"
      description_template: |
        Automated voting-power reduction generated by katana.
        Validator: {moniker} ({address})
        Score: {score}/100 (tier {tier}) over {window}
        Voting power: {current_power} -> {target_power}
        Reason: {reason}
      # run_script_template: defaults to a new built-in ValoperChange(target_power) script
    raise_vp:
      score_at_or_above: 85
      window: current_year          # long window: raise_vp is the most
                                     # governance-sensitive action, so it
                                     # requires a sustained track record, not
                                     # a good recent streak
      vp_step_percent_of_self: 20
      vp_step_percent_of_total: 2
      title_template: "Raise voting power of validator {moniker} ({address})"
      description_template: |
        Automated voting-power increase generated by katana.
        Validator: {moniker} ({address})
        Score: {score}/100 (tier {tier}) over {window}
        Voting power: {current_power} -> {target_power}
        Reason: {reason}
      # run_script_template: defaults to the same new built-in ValoperChange(target_power) script

exceptions:
  - "g1protectedvalidator..."        # unchanged shape; now blocks eject AND lower_vp AND raise_vp
```

Removed entirely: `conditions.require_all`, `conditions.missed_blocks`,
`conditions.critical_alerts`, `gnomonitoring.missed_blocks_path`,
`gnomonitoring.alerts_path`.

`proposal.actions.*` follows the existing global-with-per-chain-override model
(field-by-field merge, like today's `gnokey` block): a chain can override just
`lower_vp.score_below` without restating the whole `actions` tree.
`action_priority` and `min_voting_power`/`max_voting_power_share` are
global-only for this iteration (no per-chain override) — simplest safe
default; revisit if a real multi-chain deployment needs different values per
network.

## gnomonitoring client (`internal/gnomonitoring`)

- Replace `FetchMissedBlocks` / `FetchCriticalAlerts` with a single
  `FetchReports(ctx, chain string) ([]Report, error)` hitting
  `reports_path` (`GET /api/reports/validators?chain=<chain>`), public, no
  admin token required.
- `Report` mirrors the JSON shape: `Addr`, `Moniker`, `DaysSinceLastAlert`,
  `Periods map[string]PeriodScore` where `PeriodScore` has `Score`, `Tier`,
  `SignRate`, `ProposerReliability *float64`, `VotingPower int64`,
  `CriticalCount`, `WarningCount`, `IncidentCount`, `IncidentRatePerWeek`,
  `DowntimeBlocks`, `MissedBlocks`.
- The candidate set for a cycle is simply every `Report` entry returned (the
  endpoint already excludes validators that left the valset — see
  gnomonitoring README "Valset membership" — so katana no longer needs to
  union two endpoints' addresses).
- `api_token` is kept in config (some deployments may still protect other
  endpoints katana might use later) but is not sent to `reports_path`, which
  is public.

## Rules (`internal/rules`)

```go
type ActionType string

const (
    ActionEject   ActionType = "eject"
    ActionLowerVP ActionType = "lower_vp"
    ActionRaiseVP ActionType = "raise_vp"
)

type Decision struct {
    Address, Moniker string
    Action           ActionType // "" if none
    Score            int
    Tier             string
    Window           string
    CurrentPower     int64      // actual on-chain VP this cycle (from the report)
    TargetPower      int64      // 0 for eject
    Reason           string     // human-readable, includes sub-metrics
}

func Evaluate(r gnomonitoring.Report, priority []rules.ActionType,
    actions config.Actions, bounds config.VPBounds, totalWindowVP map[string]int64) Decision
```

**Priority order.** `Evaluate` walks `priority` (from
`proposal.action_priority`) in order and returns the first action whose
threshold matches on its own configured window. This makes reordering a
config change, not a code change; adding a genuinely new action type still
requires code (it needs its own semantics), but its place in the evaluation
order does not.

**Cross-window conflicts.** Because each action reads its own configured
window, a validator's windows can disagree — e.g. `current_week` scores 95
(excellent) while `current_month` scores 28 (critical, reflecting an
incident earlier in the month that a good week hasn't erased yet, since
calendar windows are cumulative, not rolling — see gnomonitoring README "Does
the score improve over time?"). This is expected, not a bug: with the
default `action_priority`, a severe verdict from `eject`'s window always wins
over a good verdict from `raise_vp`'s window. katana is deliberately
conservative — a bad longer-window signal blocks a reward even when the
short-term trend looks good.

**VP delta model (fixed step, no extra state).** A naive "% of current
on-chain VP" delta compounds across consecutive same-direction actions (1000 →
800 → 640 → ...), shrinking asymptotically instead of applying a predictable,
escalating correction. But a step sized purely as "% of total valset VP" is
disproportionate across validator sizes: a fixed absolute step (say -400) is a
crushing single-step -400% for a 100-VP validator (immediately floored, so
`lower_vp` becomes a permanent no-op the moment it's reached) while being a
mild -8% for a 5000-VP validator. So the step is the **smaller of two
percentage caps**, each computed fresh from live data every cycle — no history
needed:

- cap #1, `vp_step_percent_of_self% * CurrentPower` — never move a validator
  by more than this fraction of its own current VP in one step (protects
  small validators from a disproportionately large single swing).
- cap #2, `vp_step_percent_of_total% * totalWindowVP` — never move a
  validator by more than this fraction of the chain's total VP in one step
  (keeps a large validator's step bounded to something meaningful at network
  scale, rather than a huge absolute jump justified only by "20% of a huge
  number").
- `step = sign * min(|cap1|, |cap2|)`; `TargetPower = CurrentPower + step`,
  clamped to `[min_voting_power, max_voting_power_share% * totalWindowVP]`
  (`totalWindowVP` = sum of every candidate's `VotingPower` for the action's
  window, from the same cycle's report — no extra API call, no stored state).
- Example (`vp_step_percent_of_self: -20`, `vp_step_percent_of_total: -2`,
  total valset VP 20 000): validator A at 100 VP → cap1 = -20, cap2 = -400 →
  step = -20 (self-cap binds) → 100 → 80, proportionate. Validator B at 5000
  VP → cap1 = -1000, cap2 = -400 → step = -400 (network-cap binds) → 5000 →
  4600, bounded. Both move by an amount appropriate to their own size *and*
  to the network's scale, and — since both caps are recomputed from live data
  every cycle — repeated triggers still don't compound (A: 100→80→64→...,
  same asymptotic-decay shape as before once the self-cap is binding, but
  now proportionate rather than crushing in one step; B: 5000→4600→4200→...,
  linear while the network-cap binds).
- If the clamped `TargetPower` equals `CurrentPower` (no-op — already at a
  bound), `Decision.Action` is cleared to `""` and logged at debug level.

`Reason` embeds the deciding score plus sub-metrics for that window, e.g.:
`"score 24/100 (tier Critical) over current_month — sign_rate 61%, 3.2
incidents/week, 1200 downtime blocks"`.

## Proposal (`internal/proposal`)

- `Target` gains `Action rules.ActionType`, `TargetPower`, `CurrentPower` (both
  read from `rules.Decision`, for template rendering).
- `Build` selects `p.Actions[target.Action]` for templates/window instead of
  the old flat `p.TitleTemplate`/`p.DescriptionTemplate`.
- Template vars gain `target_power`, `current_power`, `score`, `tier`,
  `window`, plus the sub-metric text already assembled into `reason` by
  `rules.Evaluate`.
- Two new built-in `run_script_template` defaults (one shared by `lower_vp`
  and `raise_vp`, since both are just `ValoperChange(operator, target_power)`
  — only the sign and magnitude of the delta differ, already baked into
  `target_power`) alongside the existing eject default (`Power=0`). All three
  go through the same `NewValidatorProposalRequest` / `dao.MustCreateProposal`
  crossing-script pattern documented in the existing package comment.
- `call` mode (`proposal.submit: call`) is out of scope for `lower_vp`/
  `raise_vp` in this iteration — call-mode fields stay eject-only, matching
  their current "network-specific placeholder" status per CLAUDE.md. If a
  chain sets `submit: call`, `lower_vp`/`raise_vp` actions are skipped with a
  startup validation error (fail fast, not a silent no-op).

## Lifecycle (`internal/lifecycle`)

`Gate` signature gains the last proposal's action:

```go
func Gate(last *store.ProposalRecord, rejections int, p Params) Decision
```

`store.ProposalRecord` gains `Action string`. Behavior change in `Gate`:

- `last.Status == StatusAccepted`:
  - `last.Action == "eject"` → still terminal (`deny("already ejected")`) —
    unchanged, and belt-and-suspenders with the valset safety check.
  - `last.Action` is `lower_vp`/`raise_vp` → **not** terminal; falls through
    to the same cooldown-floor check as the `default` branch (using
    `last.CreatedAt`/`last.ResolvedAt`), allowing a later VP adjustment once
    the score moves into a different band and the cooldown has elapsed.
- `StatusPending` / `StatusRejected` / cooldown-floor branches: unchanged,
  action-agnostic — one rejection-backoff/max-rejections counter per
  validator regardless of which action was rejected (a validator flapping
  between bands doesn't get a fresh rejection budget per action type).

## Store (`internal/store`)

- `proposals` table: add `action TEXT NOT NULL DEFAULT 'eject'`,
  `target_power INTEGER`, `current_power INTEGER` columns (migration,
  additive — existing rows default to `action='eject'`, correct for all
  pre-migration history).
- `LastProposal`, `PendingProposals`, `RejectionCount`: unchanged queries
  (still keyed by `chain, address` only, per the lifecycle design above) —
  just select/scan the new columns into `ProposalRecord`.

## Notify (`internal/notify`)

- `Message` generation branches on `Action` instead of hardcoding "remove it
  from the valset":
  - `eject`: unchanged wording (FR-8.1/8.2/8.3 in prd.md).
  - `lower_vp`/`raise_vp` *sent*: `"A proposal for validator %s (%s) on %s has
    been sent to %s its voting power from %d to %d (%+.1f%% of total valset
    VP)."` (`%s` verb = "lower"/"raise").
  - *accepted*/*rejected*: same substitution pattern as today's eject
    messages, verb + power figures swapped in.
- dry_run notification (script attachment + gnokey command) mechanics
  unchanged — just the message text and the script content differ per action.
- `notifications` table: no schema change (already action-agnostic:
  channel/target/event/status/error/proposal_id).

## Daemon (`internal/daemon/cycle.go`)

- `fetchMetrics` step becomes a single `gnomonitoring.FetchReports` call
  (replaces the two separate missed-blocks/alerts fetches and their
  candidate-set union). The per-window total VP (for `max_voting_power_share`
  clamping) is computed once per cycle from this same response.
- `rules.Evaluate` is now called once per candidate (internally checking all
  three action bands on their respective windows) instead of once per
  candidate against one flat condition set. It needs no history — just this
  cycle's report and the resolved config.
- Everything downstream (exceptions → lifecycle gate → valset check → build →
  broadcast → notify → store) is unchanged in shape, just carries the new
  `Decision`/`Target` fields through.
- Per-cycle summary log line gains a per-action breakdown (eject / lower_vp /
  raise_vp counts) alongside the existing eligible/excepted/suppressed
  counters (§11 Observability in prd.md).

## Out of scope

- Per-chain override of `action_priority`, `min_voting_power`,
  `max_voting_power_share`.
- `call`-mode submission for `lower_vp`/`raise_vp`.
- Any change to the `eject` action's default thresholds, script, or its
  already-confirmed devnet e2e behavior (PP-5) beyond routing it through the
  new `proposal.actions.eject` config path.
- Re-deriving score-like logic from raw sub-metrics inside katana — score
  stays gnomonitoring's responsibility; sub-metrics are display-only context.
- A fourth "hold" / explicit no-action notification — silence is the no-action
  signal, as today.
- A hard cap on total consecutive steps in a streak — the VP bounds
  (`min_voting_power`/`max_voting_power_share`) already act as the natural
  stopping point (further same-direction actions become no-ops once clamped),
  and the fixed-step model needs no per-validator streak state to enforce it.
